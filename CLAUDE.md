# Bowling Roll — BACKEND (game server)

Frontend (3D client) lives at `../Tnt-skipping`. Colyseus + Mongo, ported from `C:\ThreeJS\Kayak-and-surf\Kayak-and-surf -backend`.

- `npm start` (tsx watch, port 2567), `npm run build` (tsc -> `build/`), `npm test` (mocha + `@colyseus/testing`, Mongo faked via `__setPlayersForTest`; tests share one booted server, `test/server.ts`). Node >= 22.
- One room, `world` (`src/rooms/WorldRoom.ts`, client calls `joinOrCreate("world", { userId, username, pfp })`). Client-authoritative: the server only bounds/sanitises saves (`src/sanitize.ts`). `src/db.ts` degrades to "no persistence" when `MONGODB_URI` is unset/unreachable; guests (`guest-` ids) are never saved. `/health` for Legion; `/monitor` and the playground are dev-only.
- The client keeps NO progress in the browser: this server's Mongo doc is the player's only save. A guest's (or a serverless session's) progress lasts the page only.
- Messages client -> server: `saveProgress` (the whole snapshot, debounced client-side), `identify` (`{ userId, username, pfp }` after a sign-in/out mid-session), `race` (`{ racing, distance }`, a few times a second while racing; distance clamped 0..`DISTANCE_MAX`, 0 when not racing). Server -> client (private): `progress` (the saved doc, sanitized), `noProgress` (new account, guest, or no database: the client keeps its fresh state and saves it), `serverError` (the save could not be read: saving stays off so it is never overwritten). Saves are ignored until the session's load has answered (`loaded`). A second live session on the same account is evicted. Roster (`PlayerState`): `username`, `signedIn`, `pfp` (Bloxity profile picture URL, http(s) only, max `PFP_MAX_LEN`, "" = none), `racing`, `distance` (studs this race): every client draws the other racers' heads on its distance bar and 1st/2nd/3rd podium from it (`test/Roster.test.ts`).
- Saved progress shape (`PlayerDoc`, client `src/progress.js` `snapshot()` minus the session-only `playStart` / `playClaimed`, sanitized by `src/sanitize.ts`): `skill`, `wins` (the currency), `rebirths`, `throws`, `bestDistance` (m, `$max` so it never drops), `playtime` (s, all sessions), `spent`, owned/equipped pairs `tnts`/`tnt` and `trails`/`trail` ("" = none; the equipped id must be owned), `pets[] { id, kind, variant, equipped, locked }` (equipped capped at `petSlots`), `nextPet`, `petSlots`, `petsSeen[]` ("kind:variant"), `indexClaimed`, `eggs { id: n }`, `potions { id: n }`, `boostUntil { id: epoch ms }` (at most `BOOST_MAX_MS` ahead), `daily { streak, last }`, `worlds[]` (unlocked world ids, kept through rebirths), `world` (the world the player is in, must be in `worlds` when the save carries it, "" = the start world), `lastSeen`. The old spin / daily server features below are unused by the Tnt-skipping client.
- Spin wheel (`src/spin.ts`, constants `SPIN_*`): server-authoritative, unlike the rest of the save. Each session's `{ spins, nextAt }` lives in `spinStates` (read from the doc's `spins`/`spinAt` on load; a new player gets `SPIN_START`), one free spin accrues every `SPIN_EVERY_MS` of real time up to `SPIN_CAP` (the clock waits while capped). After the load the server sends `spins` { spins, nextAt, serverTime }; `spin` spends one, rolls a `SPIN_WEDGES` id by weight and answers `spinResult` { ok, id, spins, nextAt, serverTime } (or { ok: false, reason: "loading" | "none" }), then writes `spins`/`spinAt` itself. `saveProgress` never carries them (not in sanitize.ts). Guests / no-DB sessions keep theirs in memory for the connection. The client grants the prize (its `SPIN.wedges` by id).
- Daily Reward (`src/daily.ts`, `DAILY_DAYS` = the client's `DAILY.days.length`): server-authoritative on the server's UTC clock. Doc fields `dailyDay` (days unlocked this cycle), `dailyLast` (UTC day index of the last unlock), `dailyClaimed[]` (0-based days), written only by the server (`saveDaily`), never by `saveProgress`. On load (`loadProgress`) the state goes into `dailies` per session, today unlocks (`rollDaily`: +1 day per new UTC day, capped; all claimed -> back to day 1) and the client gets `daily` { unlocked, claimed, nextAt, serverTime }. `claimDaily` { day } answers `dailyResult` { ok, day, reason?: "loading" | "locked" | "save", ...view } (ok only once stored); `dailyRefresh` re-rolls after midnight and answers `daily`. Guests / no-DB sessions keep theirs in memory for the connection. Tests: `test/Daily.test.ts` (shared fake Mongo in `test/fakePlayers.ts`).
- Leaderboards (`src/leaderboard.ts`, `test/Leaderboard.test.ts`): the client plaza's four boards. Top `LEADERBOARD_SIZE` saved players by each of `LEADERBOARD_STATS` (`wins`, `playtime`, `bestDistance` = Best Throw, `skill`), read with find/sort/limit into one process-wide cache refreshed at most every `LEADERBOARD_EVERY_MS`; each player's own rank = countDocuments(stat > theirs) + 1 (null for guests / no score). Server -> client `leaderboard` { boards: { stat: [{ name, value }] }, ranks: { stat: n | null } }, sent after each load and to everyone every `LEADERBOARD_EVERY_MS` (room clock). `connectDb` creates a descending index per stat. The test fake supports just that find/countDocuments shape.
- Presence (`src/presence.ts`, `test/Presence.test.ts`; client `src/net.js` + `src/remotePlayers.js`): what the others draw in the world, relayed through the roster as sent, only bounded. Roster fields `x`/`y`/`z` (feet, world metres), `yaw` (wrapped to -PI..PI), `speed` (m/s), `air` (off the ground: the remote jump animation), `tnt` / `trail` (catalog ids matching `ID_PATTERN`, "" = none), `pets` ("kind:variant,...", at most `PRESENCE_PETS_MAX`), `avatar` (Bloxity look JSON `{ equipped, proportions, skin }`, at most `AVATAR_MAX_LEN`, never parsed: other clients dress the rig with it, so remote players show their Bloxity skins). Messages `pose` { x, y, z, yaw, speed, air } (~10/s, bounds `POSE_BOUNDS`), `loadout` { tnt, trail, pets: [{ kind, variant }], world }, `setAvatar` { avatar }; the join options may carry `pose`, `loadout` and `avatar` too. **`fx`** { type: throw | fly | skip | boom | end, x, y, z, vz, spin, k, zone, tier, tnt, trail }: a throw's visible moments (the TNT in flight ~15/s, each skip, the blast), cleaned by `cleanFx`, rate-limited to `FX_PER_SECOND` per client and broadcast to everyone else with the sender's `id` (not to the sender); the client draws the arm animation, the TNT, smoke trail, skip puffs and a lighter blast (shockwave, fireball, particles) from them.
- `src/constants.ts` bounds must cover the client's `src/config.js` (catalog ids match `ID_PATTERN`, incl. engine `ladder-N`; currency up to ~3.6e28). A contract change goes in both projects.
- CI/CD: `.github/workflows/deploy.yml` tests on PRs and pushes to `main`/`dev`; pushes also build+push a GHCR image and deploy to Bloxity Legion (`main` = prod, `dev` = dev), sending `roomSize` = `ROOM_MAX_CLIENTS` read from `src/constants.ts` (keep it 2-100 for party play; no `seatCap`: the matchmaker sizes pods).
